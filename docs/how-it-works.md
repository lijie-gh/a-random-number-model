# 这个模型为什么能用 0 次训练做到「随机吐一个数」

`random-number-gguf` 不是「训练了一个随机数生成器」，而是**把概率分布手写进权重里**。
它本质上是一台「只会让采样器在 N 个等高的柱子里选一个」的机器。

下面所有数字都是真实的：可以用 `python tools/make_random_gguf.py --inspect <文件>` 复现。

---

## 1. 结构

| 项 | 值 |
|---|---|
| 架构 | `llama`（GGUF v3，F16） |
| 层数 | 1（attention / FFN 权重全 0，等价于没有） |
| 隐藏维度 | 256 |
| FFN 维度 | 256 |
| 注意力头 | 1（head_dim = 256） |
| 上下文长度 | 8192（实际只用得到 2 个 token） |
| 词表 | 259（0/1、0~9）/ 350（0~100） |
| 参数 | 591,616 / 638,208 |
| 量化 | F16 / Q8_0 / Q4_K_M / Q4_K_S / Q3_K_M / Q2_K |

**为什么不能 0 层？** Ollama 的 `ollama create` 对 `block_count=0` 直接回 HTTP 500——
llama.cpp 要求至少一层。所以「0 层」只能是「1 层但全是 0」，行为上完全等价。

权重一共 10 个张量，其中 7 个是纯 0：

| 张量 | 形状 | 内容 |
|---|---|---|
| `token_embd.weight` | (V, 256) | **只有两种行**：one-hot 第 0 位 / one-hot 第 1 位 |
| `output.weight` | (V, 256) | 第 0 维、第 1 维是 ±100，其余全 0 |
| `output_norm.weight` | (256) | 全 1 |
| `blk.0.attn_{q,k,v,output}.weight` | (256, 256) | 全 0 |
| `blk.0.ffn_{gate,up}.weight` | (256, 256) | 全 0 |
| `blk.0.ffn_down.weight` | (256, 256) | 全 0 |

`tie_word_embeddings = false` —— 输入矩阵和输出矩阵必须解耦，因为它们的角色完全不同
（一个负责「把输入抹平」，一个负责「只在数字和 EOS 上抬杠」）。

---

## 2. 第一步：让隐藏状态与输入无关

每个 token 的 embedding 只有两种可能：

```
e_in  = [1, 0, 0, 0, …, 0]     ← BOS、UNK、以及 256 个字节 token 里所有非数字的
e_num = [0, 1, 0, 0, …, 0]     ← 每一个「数字 token」自己
```

关键在于：**所有非数字 token 共用同一个 `e_in`**，所有数字 token 共用同一个 `e_num`。
没有第三个向量。

于是残差流在任何位置都只能是这两种之一：

```
h = RMSNorm(emb[上一个 token]) = 15.9796 × emb[上一个 token]
```

（1/sqrt(1/256 + 1e-5) = 15.9796，这就是 RMSNorm 对 one-hot 做出来的恰好是常数倍。）

因为 attention 和 FFN 全是 0，`h` 不会被任何「上下文」污染——**这个模型里根本不存在能读取上下文的路径**。
所以：

> 隐藏状态只取决于「上一个 token 是不是数字」，与输入内容、输入长度、历史对话、系统提示词全部无关。

这就是「不管用户输入什么」的数学来源。

---

## 3. 第二步：让 N 个选项完全等高

输出矩阵只有两列参与（第 0 维、第 1 维），其余 254 维全是 0，所以只有这两列能影响 logits：

```
out[:, 0] = -100        # 所有行先压平
out[:, 1] = -100
out[每个数字 token, 0] = +100    # 只有数字被抬起
out[EOS,          1] = +100    # 只有 EOS 被抬起
```

代入 `h = [15.9796, 0, …]`（状态 A）：

```
logits = out @ h = 15.9796 × out[:, 0]
       = +1597.96   对每个数字 token（完全相等）
       = -1597.96   对其它所有 token
```

softmax 只看相对大小，于是这 N 个数字的概率是**严格相等**的 1/N：

| 版本 | 每个取值的概率 | 与 1/N 的误差 |
|---|---|---|
| 0/1 | 0.500000 | 0 |
| 0~9 | 0.100000 | 0 |
| 0~100 | 0.009901 | ~1e-16（float32 舍入） |

**这就是这个模型里唯一的「智能」**：它把 N 个柱子摆成一模一样高。
接下来是谁在制造随机性？是采样器。`temperature=1` 时采样器直接从 softmax 分布里抽，
于是每次抽到哪个数字是真的随机——**不是模型学会的随机，是 softmax 均匀分布 + 采样器的随机性**。

---

## 4. 第三步：吐完一个数就自己停

采样出数字之后，下一个 token 的输入是那个数字 token，它的 embedding 是 `e_num`：

```
h = [0, 15.9796, 0, …]
logits = 15.9796 × out[:, 1]
       = +1597.96   只对 EOS
       = -1597.96   对其它一切（包括所有数字）
```

EOS 与次高项相差 3195.9，softmax 之后 EOS 的概率是 1 - 1.1e-16。
所以模型**一定**在第二个 token 吐出 EOS，生成就此结束。

这就是为什么它不需要 `num_predict=1` 就只输出一个数字：停是模型自己决定的，不是外面截断的。
（Ollama 的响应里 `eval_count=2`、`done_reason=stop` —— 一个数字 + 一个 EOS。）

## 5. 词表上的三条硬约束

这三条是踩出来的，违反任何一条都会直接崩或者串味：

### ① 同一个 token 串不能出现两次

llama.cpp 加载词表时有这一行断言：

```
GGML_ASSERT(id_to_token.size() == token_to_id.size()) failed
```

所以**不能**既保留 gpt2 的字节 token `"0"`，又新建一个内容 token `"0"` 当数字用。
本项目的做法：

- **单字符取值**（`0`~`9`、`0`/`1`）→ 直接复用 256 个 gpt2 字节 token 里的那一个，不新建
- **多字符取值**（`10`~`100`）→ 才新建内容 token（`"10"`、`"100"` …）

### ② 内容 token 必须让编码器「永远吐不出来」

词表里 `merges` 是空的，所以编码器只能逐字节切词。
这样 `"100"` 这个内容 token 虽然存在于词表，但任何输入都不会被切成它——
它只能被**生成**，不能被**读入**。天然杜绝了「用户输入 100 就被当成数字 token」的情况。

### ③ 数字 token 的 embedding 就是「该停了」的信号

这是本设计的一个已知边角：如果**绕过 chat 模板**、直接走补全接口，输入以数字结尾
（比如 `"5"`），模型会认为「上一个 token 是数字 → 该停了」，于是输出空。

对话模式不受影响，因为 GGUF 里的 chat template 是：

```
{{ bos_token }}
```

它把用户正文整段丢弃，只渲染出一个 `<s>`。所以无论用户在对话里说什么，进模型的永远只有 BOS。
（这既是双保险，也顺手绕掉了上面的边角。）

## 6. 为什么量化不会破坏它

- 所有非数字 embedding **完全相同**，量化是对每个 32 元素块独立做的，
  完全相同的行量化之后仍然完全相同 → 「输入无关」不受影响。
- 所有数字 token 的输出行**完全相同**，同理 → 均匀性不受影响。
- 唯一要保住的是「数字行 > 其它行」和「EOS 行 > 其它行」这两个不等式。
  原始 logit 差是 3195.9，Q2_K 这种 2 bit 量化也只会把它压到几百，符号绝不会翻。

实测：18 个文件（3 族 × 6 档）全部通过均匀性检验，见根目录 README 的实测表。

---

## 7. 一句话总结

> 这个模型没有「学会」随机，它只是被摆成了一个**恰好等高的骰子**。
> 层全 0 保证输入传不进来，embedding 只有两种取值保证上下文无效，
> 输出矩阵的 ±100 保证 N 个选项概率严格相等，EOS 那一列保证它吐一个就停。
